# Plan 2 — API : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** Livrer l'API NestJS de Digimmo : comptes (inscription, connexion, mot de passe oublié, RGPD, rôle admin), projets avec terrain et PLU, plans stockés dans MongoDB et validés côté serveur par `@digimmo/domain`, catalogue de meubles — le tout testé de bout en bout contre de vraies bases.

**Architecture :** NestJS en couches (contrôleur → service → dépôt) dans `apps/back`. PostgreSQL via TypeORM (migrations versionnées = MLD du dossier) pour comptes, projets, catalogue ; MongoDB via Mongoose pour les documents de plan. Validation de toutes les entrées par des schémas Zod (ceux de `@digimmo/domain` pour le plan, le terrain et le PLU) au travers d'un seul `ZodValidationPipe`. Session = JWT dans un cookie `httpOnly`, utilisateur rechargé à chaque requête.

**Tech Stack :** NestJS 11, TypeORM + `pg`, `@nestjs/mongoose`, `@nestjs/jwt`, `cookie-parser`, `argon2`, `@nestjs/throttler`, `helmet`, `nodemailer`, Zod 4, Jest + supertest, Docker Compose (PostgreSQL 17, MongoDB 8, Mailpit).

**Spec :** `docs/superpowers/specs/2026-11-23-digimmo-design.md` (§2 objectifs comptes, §6 Architecture — Back et Données, §8 Qualité et sécurité).

## Global Constraints

- Node ≥ 22.12 ; le back reste en CommonJS et importe `@digimmo/domain` (build du domain avant les tests).
- Unités : centimètres entiers ; le plan est validé par `parsePlan` puis `validatePlan` de `@digimmo/domain`.
- Un plan au **format invalide est refusé (400)** ; un plan qui viole des **règles métier est enregistré** (brouillon) avec son résultat de validation.
- Mot de passe haché **argon2** ; session **JWT dans un cookie `httpOnly`, `Secure` (hors dev/test), `SameSite=Lax`** ; limitation de débit sur la connexion et sur la demande de réinitialisation.
- Mot de passe oublié : jeton aléatoire **à usage unique, stocké haché, valable 1 h**, envoyé par e-mail ; **réponse identique que l'adresse existe ou non**.
- Rôles `user` (défaut) et `admin` ; l'admin gère le catalogue, **n'a pas accès aux projets des autres** ; premier admin créé **par script de seed, jamais via l'API**.
- RGPD : export JSON de toutes les données de l'utilisateur ; suppression du compte **avec confirmation par mot de passe**, en cascade (PostgreSQL + MongoDB).
- Un utilisateur n'accède qu'à ses projets : une ressource d'autrui répond **404** (on ne révèle pas son existence).
- Validation stricte des entrées (tout champ inconnu rejeté), CORS restreint à l'origine du front, en-têtes `helmet`, secrets hors dépôt (`.env.example` documenté).
- Messages d'erreur renvoyés au client en **français**.
- TDD : chaque comportement commence par un test qui échoue.

## Review Focus

1. **Accès au projet ou au plan d'un autre utilisateur** par son id (`GET/PATCH/DELETE /projects/:id`, `GET/PUT /projects/:id/plan`) → 404, aucune donnée renvoyée ni modifiée. Test : Tâches 7 et 8.
2. **E-mail avec majuscules ou espaces** (`" Alice@Example.com "`) : inscription puis connexion avec `alice@example.com` fonctionne ; une seconde inscription avec une autre casse → 409. Test : Tâche 4.
3. **Jeton de réinitialisation réutilisé ou expiré** → 400, mot de passe inchangé. Test : Tâche 5.
4. **Corps de plan trop gros (> 1 Mo) ou JSON mal formé** → 413 / 400 propres, jamais 500. Test : Tâche 8.
5. **Cookie encore valide d'un compte supprimé** → 401 sur toute route protégée. Test : Tâche 9.
